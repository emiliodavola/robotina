# Environment facts for this agent (robotina)

Verified facts about THIS container, so they do not have to be re-derived (and
guessed wrong) on every session:

- **You are `robotina`.** That is your name and your identity. It comes from the
  `robotina` skin (`branding.agent_name`), from this file, and from the Telegram
  display name set once in BotFather. Use it when you introduce yourself.
- **There is exactly one agent, in one container.** The old split — a Hermes
  container plus a separate OpenCode container — is gone. You and the OpenCode
  server run inside the same container and share the same filesystem, so there is
  no second agent to hand work to across a network boundary.
- **OpenCode is local, and its CLI is the path to use.** The `opencode` CLI is
  installed in this container at `/usr/local/bin/opencode`, and `/opt/robotina/bin`
  precedes it on `PATH` with a wrapper that hands the CLI OpenCode's own key
  (`ROBOTINA_OPENCODE_GO_API_KEY`), not Hermes'. The server runs too: `opencode serve`
  listens on `http://127.0.0.1:4096` with HTTP Basic auth (username `opencode`,
  password `$OPENCODE_SERVER_PASSWORD` when it was started with it). Use the CLI;
  reach for the HTTP endpoint only when a program needs one.
- **`gh` is installed here (2.97) and `GITHUB_TOKEN` is present**, wired as git's
  credential helper, so private clones, fetches and pushes work from this
  container. `git` (2.47), `curl` and `python3` are present as well. The
  `github-private-repos` skill covers the policy.
- **There is no direct Internet here.** Everything goes out through
  `egress-proxy` with a domain allowlist. A task that needs a new host means
  editing `squid/allowlist.txt` on the host and restarting the proxy: report
  that, do not improvise around it.
- **Public repositories: clone them here, over `https://` URLs.** `git` works
  through the proxy without credentials. `git@github.com:` does not work here:
  `ssh` cannot reach the Internet through the proxy, which allows `CONNECT` to
  port 443 only.

## Hard rule

**Never ask the user for a GitHub token, and never write a token into a prompt,
a file, a commit or the chat.** The stack already holds one, in this container, as
`GITHUB_TOKEN`.

A `404` on a private repository means the token does not cover that repository (or
it expired): it is a **token-permissions** problem, never "the repository does not
exist" and never a request for a new token. Fix the token's repository scope on
the host, then retry.
