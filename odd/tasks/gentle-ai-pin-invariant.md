# Feature: gentle-ai-pin-invariant

## Goal

Close #74: `gentle-ai` MUST carry the same two invariants `engram` already carries (AC11), because
it is the only baked tool that was left without them and it is the one the agent is most likely to
try to update from inside the container:

1. the image **publishes the pin** it baked, and the healthcheck fails when the binary that runs
   reports another version;
2. `command -v gentle-ai` resolves to the image's own copy, so a copy in the agent's HOME
   (`/opt/data/.local/bin`, which precedes `/usr/local/bin` in the stack's `PATH`) cannot shadow the
   baked binary unnoticed.

The self-upgrade failure itself (`EACCES` creating a temp file in a root-owned `/usr/local/bin`) is a
defect of `gentle-ai`, not of this stack: the upstream fix is to detect the non-writable directory
before downloading and return `ManualFallbackError` (upstream issue, out of scope here). What this
stack owns is making the failure **unnecessary and loud**: the correct path is documented where the
operator reads it (README) and where the agent reads it (`AGENTS.md`), and the wrong path is
detected by the healthcheck.

Branch: `fix/issue-74-gentle-ai-pin-invariant`, off `main`. Owner: `emiliodavola`.

## Non-goals

- No change to `gentle-ai` upstream and no local patch to its update path. The opaque `EACCES` is
  reported upstream, not worked around here.
- No change to what `/usr/local/bin` is or to the app uid. The directory stays root-owned on purpose:
  that is exactly why the self-upgrade path cannot work and the pin is the only supported update.
- No image rebuild or container recreate in this change. The healthcheck addition is guarded by
  `[ -n "$ROBOTINA_GENTLE_AI_VERSION" ]`, so the running (pre-change) container skips it instead of
  failing falsely; proving it live belongs to the next rebuild.
- No new maintenance script: `scripts/bump-tools.sh` already knows `gentle-ai` and already warns that
  a bump needs its own verification.

## Diagnosis (measured, read-only against the live stack, 2026-09-28)

1. `docker compose exec robotina sh -c 'echo "$ROBOTINA_GENTLE_AI_VERSION"'` → **unset**, while
   `ROBOTINA_ENGRAM_VERSION` → `2.2.1`. The pin `ARG GENTLE_AI_VERSION=3.1.0` is baked but never
   published to the container.
2. `/usr/local/bin/gentle-ai --version` → `gentle-ai 3.1.0` (one line, no banner), equal to the pin.
3. `command -v gentle-ai` → `/usr/local/bin/gentle-ai` **today**, and there is no
   `/opt/data/.local/bin/gentle-ai` — so the shadow is not present now, it is simply **undetected**
   if it appears. Same measurement for `engram`, which is why AC11 exists for it.
4. As the app uid: `s6-setuidgid hermes test -w /usr/local/bin` → NOT WRITABLE (`root:root 755`).
   The self-upgrade stages `<binary>.new` **beside** the destination (the publish is an atomic
   `rename`), so it dies with `EACCES` on the temp file: it can never succeed here.
5. `grep` for `bump-tools` / `self-upgrade` in `README.md`, `README.en.md` and `SECURITY.md` → **0
   hits**. The correct update path lives only in a comment in `robotina/Dockerfile` §8.
6. There is **no `AGENTS.md`** in this repository, so the agent has no project instruction to read.
   The `AGENTS.md` files found under `/opt/gentle-ai-stage` are generated by `gentle-ai` itself and
   are not ours to edit.

## Shape

1. `robotina/Dockerfile`: publish `ENV ROBOTINA_GENTLE_AI_VERSION=${GENTLE_AI_VERSION}` next to
   `ROBOTINA_ENGRAM_VERSION`, with the same comment style (why it is published, what detects what).
2. `robotina/healthcheck.sh`: a fourth check — compare the absolute binary's reported version against
   the published pin **and** require `command -v gentle-ai` to resolve to the image's copy. Same
   shape, wording and failure behaviour as the `engram` block; guarded by the variable being set.
3. `openspec/specs/agent-container/spec.md`: a new requirement (**AC13**) that generalises the
   published-pin invariant to every tool the image pins, with scenarios and shell-level PROOFs, plus
   the note that the build is what publishes it.
4. `README.md` and `README.en.md`: an operator-facing section that states the one supported update
   path for the baked tools (`scripts/bump-tools.sh --write <tool>` + rebuild) and that the in-container
   self-upgrade of `gentle-ai` is **not supported** because `/usr/local/bin` is root-owned and the
   services run as `hermes`.
5. `AGENTS.md` (new, repository root): the short rule an agent working in this repository reads first,
   with the same invariant and the pointer to `bump-tools.sh`.
